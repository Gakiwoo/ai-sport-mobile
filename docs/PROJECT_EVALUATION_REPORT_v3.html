AI Motion Tracker 是一款基于 MediaPipe Pose 的实时运动追踪 App（Android/iOS）， 支持跳绳、开合跳、深蹲、立定跳远、纵跳摸高、仰卧起坐 6 种运动。 采用 WebView + Blob URL 注入 架构运行 MediaPipe WASM， 以 策略模式 组织计数器，使用 Repository 模式 抽象数据层。 项目整体工程化水平高，CI/CD、ADR、i18n、Sentry 监控、Maestro E2E 均已落地。

架构分层

Screens (页面编排) └── Hooks (状态 & 逻辑复用: useWorkout, useWebViewMessageHandler, useExerciseFeedback) └── Services (业务逻辑: Counter 策略模式, Auth, Storage, Sync, MediaPipe) └── Utils (工具: Kalman 滤波, 自适应帧率, CDN 策略, 姿态质量) └── Types (完整类型定义体系)

三、架构设计合理性与可扩展性

评分
4.5/5
分层清晰 · 策略模式 + Repository · 无循环依赖

✅ 优势

  • 策略模式 (ExerciseCounter) — 新增运动只需继承基类实现 5 个抽象方法，设计文档完备 (ADR-002)
  • Repository 模式 (IWorkoutRepository) — 数据层接口抽象，支持后续切换后端（如云端同步）而不改上层
  • WebView + Blob URL 架构 (ADR-001) — 合理的折中方案：离线可用、绕过 WebView 缓存不可靠问题
  • CDN 多源回退 (ADR-003) — 4 级优先级 + asyncPool 并发控制，容错性好
  • 分层清晰 — Screens → Hooks → Services → Utils → Types，职责单一
  • Context API 适度使用 — 仅 Auth + Locale 两个全局 Context，避免过度工程化
  • 无循环依赖 — 模块导入拓扑单向流动
  • 3 份 ADR 文档 — 关键架构决策有记录、有对比方案、有选型理由

⚠️ 问题清单

  • 警告
    StorageService 与 WorkoutRepository 共享存储 Key
    旧 StorageService (v1.0) 和新 WorkoutRepository (v1.2) 操作同一 AsyncStorage key，存在数据冲突风险。应废弃 StorageService 或明确迁移机制
  • 建议
    缺少依赖注入容器
    当前 hooks 直接 import 具体服务实现，单元测试需要模块级 mock。建议引入轻量 DI 或 factory 模式
  • 建议
    WebView 通信耦合度较高
    useWebViewMessageHandler (332 行) 承载了消息路由、Blob 注入、运行时控制等多个职责，可考虑拆分

四、性能瓶颈与优化空间

评分
4.0/5
自适应帧率 + Kalman 滤波 · APK 目录需清理

✅ 优势

  • 自适应帧率 (adaptivePoseRuntime) — 根据设备性能动态调整检测频率，低端机自动降频
  • Kalman 滤波 + 滑动窗口 — 姿态信号去噪，减少计数抖动
  • WebView GPU 加速 — androidLayerType: 'hardware' 已配置
  • 模型本地缓存 — 首次 22MB 下载后零网络依赖，离线可用
  • 分块注入优化 — 大文件 8x 增大分块，小块一次性注入，消除分块传输延迟
  • PerformanceMonitor — FPS / 推理耗时实时监控，低帧率事件记录

⚠️ 问题清单

  • 严重
    APK 构建目录 ~1.5GB 未清理
    AI Sport APK/ 目录包含 17 次历史构建的 APK 文件，约 1.5GB。虽已 .gitignore 但仍占用磁盘。建议归档旧版本或添加清理脚本
  • 警告
    WebView postMessage 序列化开销
    每帧 Pose 数据通过 JSON.stringify / JSON.parse 在 JS ↔ Native 间传递，高频场景 (30fps) 下存在可感知开销。中长期应考虑 expo-camera + 原生 MediaPipe 方案
  • 建议
    useExerciseFeedback 计算开销
    (369 行) 每帧执行角度计算、质量评分、反馈生成。可考虑 throttle 非关键反馈更新频率

五、安全性漏洞风险

评分
4.0/5
Sentry DSN 待填入 · WebView 安全加固完善

✅ 优势

  • 无硬编码密钥 — 未检测到密码、Token、API Key 等硬编码
  • WebView CSP 加固 — originWhitelist 限制 5 个可信源，allowFileAccess: false
  • Cookie 隔离 — sharedCookiesEnabled: false
  • Bearer Token 认证 — v1.1.0 移除了 Cookie 手工管理，改用标准 Bearer Token
  • expo-secure-store — 敏感数据 (Token) 使用 Keychain / Keystore 存储
  • Token 刷新竞态保护 — refreshOnce() 单例锁防止并发刷新
  • 依赖安全覆盖 — ws, shell-quote, postcss 等已知漏洞依赖已 override

⚠️ 问题清单

  • 警告
    Sentry DSN 使用占位符
    EXPO_PUBLIC_SENTRY_DSN 当前为占位符 YOUR_SENTRY_DSN_HERE，生产环境崩溃无法上报。需填入真实 DSN 或明确禁用
  • 建议
    无 HTTPS 强制检查
    apiBaseUrl.ts 在开发环境使用 localhost:5173 (HTTP)，生产切换到 gakiwoo.com，但未做协议强制校验
  • 建议
    缺少 SSL Pinning
    当前网络请求未做证书固定，存在中间人攻击风险
  • 建议
    代码混淆未配置
    APK 构建未启用 ProGuard/R8 混淆，逆向工程门槛较低
